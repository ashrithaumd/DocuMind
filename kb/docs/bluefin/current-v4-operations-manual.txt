Current forecasting, version 4 — operations guide

Version 4.6, 2026. Published by Bluefin Analytics. This edition replaces all earlier versions of the Current operations guide.

1. How to use this document

This document is for the people who keep Current running: support engineers, data engineers and customer administrators. Section 2 lists the
key specifications. Section 3 covers safety and access. Section 4 is the reference of
every error code, with what it means, the usual causes and what to do. Section 5 lists
the configuration keys with their identifiers and service intervals. Section 6 has step-by-step
procedures, and section 7 the maintenance schedule. When you open a ticket about
Current, always quote the error code and the identifier from these tables exactly as
written: our tooling searches on them.

2. Key specifications

- Forecast horizon: 8 weeks, daily
- Refresh: nightly at 02:00 Eastern
- Accuracy target: WAPE under 28 percent at store-product-week
- History needed: at least 2 years of point-of-sale data
- Largest tenant: about 1.2 billion store-product-day rows
- Export formats: daily CSV drop, REST API
- API rate limit: 600 requests per minute
- Data retention: forecast history kept for 400 days

3. Safety and access

Production changes need a second engineer to review them. Customer data stays in the customer's own schema: never copy it to a laptop or a ticket. Use the read-only role for investigation and the admin role only to apply a fix.
Every intervention is recorded against a ticket in the SUP queue. A ticket id looks like
SUP-21278. Never close a ticket without recording what was changed, and never
change two things at once: if the problem comes back, you need to know which change mattered.

4.7 Troubleshooting by symptom

Symptom (ingestion): One store's figures jump wildly from day to day.
What to do: Check the ingestion input for that store for duplicated or missing days before suspecting the model.

Symptom (ingestion): Exports arrive, but some rows are missing at the end of the file.
What to do: Compare row counts between the ingestion output and the export; a size limit may be cutting the file.

Symptom (ingestion): Customers say their numbers look a day behind.
What to do: Check the ingestion run history for the last two nights; a silent failure usually shows as a missing run, not an error.

Symptom (ingestion): Nightly jobs finish later every week.
What to do: Review the ingestion timings and queue depth; a growing backlog points to too few workers.

Symptom (feature store): A customer can sign in but sees an empty workspace.

6. Procedures

6.1 Re-running a failed nightly job
  1. Find the failed run in the scheduler view and note its run id.
  2. Read the first error in the log, not the last; later errors are usually consequences.
  3. Fix the cause (credentials, schema, quota) before re-running.
  4. Re-run with the same run date so outputs land in the right partition.
  5. Tell the customer if their data was more than 6 hours late.

6.2 Rotating a customer's warehouse credentials
  1. Ask the customer administrator to create the new key pair in their warehouse.
  2. Paste the public key into the connector settings; never ask for the private key by email.
  3. Run the connection test.
  4. Remove the old key only after a successful nightly run with the new one.

6.3 Rolling back a configuration change
  1. Open the configuration history and find the last known-good version.
  2. Compare it with the current version and confirm the change you want to undo.
  3. Restore it and record the ticket id in the change note.
  4. Watch the next scheduled run end to end.

6.4 Onboarding a new customer tenant
  1. Create the tenant schema from the template; never copy another customer's schema.
  2. Set the time zone, currency and fiscal calendar before loading any data.
  3. Load two years of history and run the data-quality report.
  4. Agree the first go-live date with the customer only after the report is clean.

6.5 Investigating repeated ingestion errors
  1. List every ingestion error from the last 7 days and group them by code.
  2. Clean the sensor surface with a dry microfibre cloth.
  3. Check whether the errors started after a release or a site change.
  4. Fix one cause at a time and watch for 24 hours before closing the ticket.

6.6 Investigating repeated feature store errors
  1. List every feature store error from the last 7 days and group them by code.
  2. Inspect the connector and reseat it.
  3. Check whether the errors started after a release or a configuration change.
  4. Fix one cause at a time and watch for 24 hours before closing the ticket.

6.7 Investigating repeated training errors
  1. List every training error from the last 7 days and group them by code.
  2. Check the site network dashboard for drops.
  3. Check whether the errors started after a release or a network change.
  4. Fix one cause at a time and watch for 24 hours before closing the ticket.

6.8 Investigating repeated scoring errors
  1. List every scoring error from the last 7 days and group them by code.
  2. Check the event log for the five minutes before the error.
  3. Check whether the errors started after a release or a configuration change.
  4. Fix one cause at a time and watch for 24 hours before closing the ticket.

6.9 Investigating repeated export errors
  1. List every export error from the last 7 days and group them by code.
  2. Confirm the unit is on the current release.
  3. Check whether the errors started after a release or a schema change.
  4. Fix one cause at a time and watch for 24 hours before closing the ticket.

6.10 Investigating repeated scheduler errors
  1. List every scheduler error from the last 7 days and group them by code.
  2. Inspect the connector and reseat it.
  3. Check whether the errors started after a release or a site change.
  4. Fix one cause at a time and watch for 24 hours before closing the ticket.

7. Maintenance schedule

Every run: check the ingestion; inspect the training; review the scheduler event log for repeated warnings.

Daily: check the ingestion; inspect the scheduler; review the scoring event log for repeated warnings.

Weekly: check the scoring; inspect the scheduler; review the training event log for repeated warnings.

Monthly: check the scoring; inspect the ingestion; review the scheduler event log for repeated warnings.

Quarterly: check the export; inspect the training; review the scoring event log for repeated warnings.
