Tide dashboards — operations guide

Version 7.11, 2026. Published by Bluefin Analytics. This edition replaces all earlier versions of the Tide operations guide.

1. How to use this document

This document is for the people who keep Tide running: support engineers, data engineers and customer administrators. Section 2 lists the
key specifications. Section 3 covers safety and access. Section 4 is the reference of
every error code, with what it means, the usual causes and what to do. Section 5 lists
the configuration keys with their identifiers and service intervals. Section 6 has step-by-step
procedures, and section 7 the maintenance schedule. When you open a ticket about
Tide, always quote the error code and the identifier from these tables exactly as
written: our tooling searches on them.

2. Key specifications

- Dashboards: 25 in Standard, unlimited in Enterprise
- Refresh: every 4 hours; hourly in Enterprise
- Load time: under 3 seconds at p90 for up to 500 million rows
- Single sign-on: SAML, Enterprise only
- Exports: PDF, CSV, scheduled email
- Query timeout: 120 seconds
- Cache lifetime: 15 minutes
- Audit log retention: 13 months

3. Safety and access

Production changes need a second engineer to review them. Customer data stays in the customer's own schema: never copy it to a laptop or a ticket. Use the read-only role for investigation and the admin role only to apply a fix.
Every intervention is recorded against a ticket in the SUP queue. A ticket id looks like
SUP-66823. Never close a ticket without recording what was changed, and never
change two things at once: if the problem comes back, you need to know which change mattered.

4.7 Troubleshooting by symptom

Symptom (connector): A customer can sign in but sees an empty workspace.
What to do: Check their group mappings and permissions in the connector settings.

Symptom (connector): One store's figures jump wildly from day to day.
What to do: Check the connector input for that store for duplicated or missing days before suspecting the model.

Symptom (connector): A dashboard that used to be quick has become slow over a few weeks.
What to do: Look at the connector for growth in data volume or a filter that stopped using its cache.

Symptom (connector): Customers say their numbers look a day behind.
What to do: Check the connector run history for the last two nights; a silent failure usually shows as a missing run, not an error.

Symptom (semantic layer): A dashboard that used to be quick has become slow over a few weeks.

6. Procedures

6.1 Re-running a failed nightly job
  1. Find the failed run in the scheduler view and note its run id.
  2. Read the first error in the log, not the last; later errors are usually consequences.
  3. Fix the cause (credentials, schema, quota) before re-running.
  4. Re-run with the same run date so outputs land in the right partition.
  5. Tell the customer if their data was more than 6 hours late.

6.2 Rotating a customer's warehouse credentials
  1. Ask the customer administrator to create the new key pair in their warehouse.
  2. Paste the public key into the connector settings; never ask for the private key by email.
  3. Run the connection test.
  4. Remove the old key only after a successful nightly run with the new one.

6.3 Rolling back a configuration change
  1. Open the configuration history and find the last known-good version.
  2. Compare it with the current version and confirm the change you want to undo.
  3. Restore it and record the ticket id in the change note.
  4. Watch the next scheduled run end to end.

6.4 Onboarding a new customer tenant
  1. Create the tenant schema from the template; never copy another customer's schema.
  2. Set the time zone, currency and fiscal calendar before loading any data.
  3. Load two years of history and run the data-quality report.
  4. Agree the first go-live date with the customer only after the report is clean.

6.5 Investigating repeated connector errors
  1. List every connector error from the last 7 days and group them by code.
  2. Confirm the unit is on the current release.
  3. Check whether the errors started after a release or a network change.
  4. Fix one cause at a time and watch for 24 hours before closing the ticket.

6.6 Investigating repeated semantic layer errors
  1. List every semantic layer error from the last 7 days and group them by code.
  2. Check the site network dashboard for drops.
  3. Check whether the errors started after a release or a schema change.
  4. Fix one cause at a time and watch for 24 hours before closing the ticket.

6.7 Investigating repeated query engine errors
  1. List every query engine error from the last 7 days and group them by code.
  2. Run the built-in self-test from the service menu.
  3. Check whether the errors started after a release or a configuration change.
  4. Fix one cause at a time and watch for 24 hours before closing the ticket.

6.8 Investigating repeated cache errors
  1. List every cache error from the last 7 days and group them by code.
  2. Confirm the unit is on the current release.
  3. Check whether the errors started after a release or a schema change.
  4. Fix one cause at a time and watch for 24 hours before closing the ticket.

6.9 Investigating repeated sharing errors
  1. List every sharing error from the last 7 days and group them by code.
  2. Check the site network dashboard for drops.
  3. Check whether the errors started after a release or a schema change.
  4. Fix one cause at a time and watch for 24 hours before closing the ticket.

6.10 Investigating repeated sso errors
  1. List every sso error from the last 7 days and group them by code.
  2. Inspect the connector and reseat it.
  3. Check whether the errors started after a release or a schema change.
  4. Fix one cause at a time and watch for 24 hours before closing the ticket.

7. Maintenance schedule

Every run: check the semantic layer; inspect the cache; review the query engine event log for repeated warnings.

Daily: check the sharing; inspect the cache; review the semantic layer event log for repeated warnings.

Weekly: check the sso; inspect the connector; review the cache event log for repeated warnings.

Monthly: check the cache; inspect the sso; review the semantic layer event log for repeated warnings.

Quarterly: check the semantic layer; inspect the sso; review the sharing event log for repeated warnings.
